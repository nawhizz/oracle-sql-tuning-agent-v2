# 오라클 힌트 레퍼런스 (Phase 1)

본 문서는 단일~3 테이블 SELECT 튜닝에서 자주 사용되는 힌트만 다룬다. 각 힌트는 ① 문법 ② 효과 ③ 적용 조건 ④ 주의사항 4항을 포함한다.

힌트는 옵티마이저에 **권고**하는 것이지 강제가 아니다(특정 힌트 제외). 항상 EXPLAIN PLAN 또는 GATHER_PLAN_STATISTICS로 실제 적용 여부를 확인한다.

## 1. 옵티마이저 모드

### `ALL_ROWS`
- **문법**: `/*+ ALL_ROWS */`
- **효과**: 전체 결과 집합을 가장 빠르게 반환하는 계획 선택. 19c 기본값.
- **적용 조건**: 배치, 집계, 전체 조회.
- **주의**: 시스템 기본 모드와 동일하면 명시 불필요.

### `FIRST_ROWS(n)`
- **문법**: `/*+ FIRST_ROWS(10) */`
- **효과**: 처음 n행을 빠르게 반환하는 계획 우선.
- **적용 조건**: 페이지네이션, OLTP UI 응답.
- **주의**: 정렬·집계가 있으면 효과 제한적. n은 정수만.

## 2. 조인 순서

### `LEADING`
- **문법**: `/*+ LEADING(t1 t2 t3) */`
- **효과**: 명시한 순서를 outer로 채택.
- **적용 조건**: 작은 테이블을 outer로 두고 싶을 때.
- **주의**: 별칭이 있으면 별칭 사용. 테이블 이름 잘못 적으면 무시됨.

### `ORDERED`
- **문법**: `/*+ ORDERED */`
- **효과**: FROM 절에 등장한 순서대로 조인.
- **적용 조건**: SQL 작성 시 의도한 순서를 보존하고 싶을 때.
- **주의**: 레거시 힌트. `LEADING`이 더 명시적이라 권장.

## 3. 조인 방식

### `USE_NL`
- **문법**: `/*+ USE_NL(t2) */` 또는 `/*+ USE_NL(t1 t2) */`
- **효과**: 지정 테이블을 inner로 NESTED LOOP 조인.
- **적용 조건**: outer가 작고 inner에 효율적 인덱스가 있을 때.
- **주의**: 양쪽 다 크면 성능 급감. `LEADING`과 함께 사용.

### `USE_HASH`
- **문법**: `/*+ USE_HASH(t2) */`
- **효과**: HASH JOIN 강제.
- **적용 조건**: 양쪽 모두 크고 PGA 메모리가 충분할 때.
- **주의**: 작은 테이블이 build, 큰 테이블이 probe. PGA 부족 시 디스크 사용.

### `USE_MERGE`
- **문법**: `/*+ USE_MERGE(t2) */`
- **효과**: SORT MERGE JOIN.
- **적용 조건**: 양쪽이 이미 정렬돼 있거나 정렬 비용이 낮을 때.
- **주의**: 많은 경우 HASH JOIN이 더 빠름. ORDERED와 함께 명시 권장.

### `NO_USE_NL` / `NO_USE_HASH` / `NO_USE_MERGE`
- **문법**: `/*+ NO_USE_NL(t2) */`
- **효과**: 해당 조인 방식 배제.
- **적용 조건**: 옵티마이저가 부적절한 방식을 반복 선택할 때.
- **주의**: 대안이 자명할 때만 사용.

## 4. 인덱스 접근

### `INDEX`
- **문법**: `/*+ INDEX(t idx_name) */`
- **효과**: 지정 인덱스를 사용한 RANGE/UNIQUE SCAN 유도.
- **적용 조건**: 옵티마이저가 FULL SCAN을 선택했지만 인덱스가 더 효율적일 때.
- **주의**: 인덱스명이 틀리면 무시. 다중 인덱스 후보가 있으면 명시.

### `INDEX_DESC`
- **문법**: `/*+ INDEX_DESC(t idx_name) */`
- **효과**: 인덱스 내림차순 스캔. ORDER BY DESC + LIMIT에 유용.
- **적용 조건**: 인덱스 정렬 방향과 반대 정렬 출력이 필요할 때.
- **주의**: 옵티마이저가 자체 판단으로 우회할 수 있음.

### `INDEX_FFS`
- **문법**: `/*+ INDEX_FFS(t idx_name) */`
- **효과**: 인덱스 FAST FULL SCAN. 인덱스만으로 SELECT가 가능할 때 테이블 미접근.
- **적용 조건**: 커버링 인덱스가 있을 때 COUNT/집계.
- **주의**: 인덱스 컬럼만 SELECT 가능. NULL 미포함 컬럼이면 결과가 달라질 수 있음.

### `NO_INDEX`
- **문법**: `/*+ NO_INDEX(t idx_name) */`
- **효과**: 특정 인덱스 사용 금지.
- **적용 조건**: 비효율적 인덱스로 옵티마이저가 빠질 때.
- **주의**: 인덱스 다수일 때 대안이 자동 선택되는지 EXPLAIN PLAN 재확인.

## 5. 접근 경로

### `FULL`
- **문법**: `/*+ FULL(t) */`
- **효과**: FULL TABLE SCAN 강제.
- **적용 조건**: 큰 비율의 행을 읽거나 인덱스 클러스터링이 매우 나쁠 때.
- **주의**: 캐시 미적재면 물리 I/O 폭증. 병렬과 결합 가능.

### `INDEX_RS_ASC`
- **문법**: `/*+ INDEX_RS_ASC(t idx_name) */`
- **효과**: 인덱스 RANGE SCAN ASCENDING 명시.
- **적용 조건**: 옵티마이저가 다른 스캔 방식을 선택했지만 RANGE SCAN이 적합할 때.
- **주의**: 19c부터 권장. 11g에서는 `INDEX`로 대체.

## 6. 통계 수집

### `GATHER_PLAN_STATISTICS`
- **문법**: `/*+ GATHER_PLAN_STATISTICS */`
- **효과**: 단계별 실측치(A-Rows, A-Time, Buffers, Reads) 수집.
- **적용 조건**: 진단 목적으로 단발성 실행할 때.
- **주의**: 운영 SQL에 상시 사용 금지. 약간의 오버헤드.

### `STATISTICS_LEVEL` 세션 설정
- **문법** (힌트가 아닌 세션 설정): `ALTER SESSION SET STATISTICS_LEVEL = ALL;`
- **효과**: 세션 전체 SQL에 GATHER_PLAN_STATISTICS와 동일 효과.
- **적용 조건**: 다수 SQL을 진단할 때.
- **주의**: 세션 종료 시 해제. 운영 세션에 적용 금지.

## 7. 병렬 (Phase 1은 정보 제공만)

### `PARALLEL`
- **문법**: `/*+ PARALLEL(t, 4) */` 또는 `/*+ PARALLEL(4) */`
- **효과**: 병렬 처리 차수 지정.
- **적용 조건**: 큰 테이블의 FULL SCAN, DW 환경.
- **주의**: 동시 사용자가 많은 OLTP에서는 자원 경합. **Phase 1 범위에서는 권고하지 않음** — 제공 정보만 해석.

## 8. 기타 자주 쓰이는 힌트

### `NO_MERGE` / `MERGE`
- **문법**: `/*+ NO_MERGE(view_alias) */`
- **효과**: 인라인 뷰 병합 금지/허용.
- **적용 조건**: 인라인 뷰가 외부 쿼리와 합쳐져 비효율 계획이 나올 때.

### `PUSH_PRED` / `NO_PUSH_PRED`
- **문법**: `/*+ PUSH_PRED(view_alias) */`
- **효과**: 술어를 뷰 내부로 푸시.
- **적용 조건**: 뷰 내부에서 필터링이 가능할 때.

### `OPT_PARAM`
- **문법**: `/*+ OPT_PARAM('optimizer_index_cost_adj' 50) */`
- **효과**: SQL 단위로 옵티마이저 파라미터 임시 변경.
- **적용 조건**: 시스템 파라미터를 바꾸지 않고 단발 테스트할 때.
- **주의**: 운영에 남기면 의도 파악이 어려움. 주석으로 이유 명시.

### `MATERIALIZE` / `INLINE`
- **문법**: `WITH cte AS (SELECT /*+ MATERIALIZE */ ...)`
- **효과**: CTE를 임시 테이블로 구체화 / 인라인 처리.
- **적용 조건**: CTE를 여러 번 참조하거나 한 번만 참조할 때 분기.

## 힌트 사용 일반 원칙

1. **근거 데이터 확보 후** 사용: 통계·실행 계획 없이 힌트로 우회하지 말 것.
2. **별칭 일관성**: SQL의 테이블 별칭과 힌트의 식별자가 정확히 일치해야 한다.
3. **검증 의무**: 힌트 적용 후 반드시 `EXPLAIN PLAN` 또는 `DISPLAY_CURSOR`로 의도대로 적용됐는지 확인.
4. **최소 침습**: 가능한 가장 적은 힌트로 목표 달성. 힌트 다수 사용은 옵티마이저 진화 시 부채.
