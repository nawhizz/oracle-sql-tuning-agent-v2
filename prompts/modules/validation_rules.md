# 정보 검증 규칙 (FR-4)

`INFO_VALIDATION` 상태에서 사용자가 제공한 응답을 다음 4종 검증을 통과시킨 뒤에만 `TUNING`으로 진행한다. 어떤 검증이라도 실패하면 `INFO_REQUEST`로 루프하거나(또는 권한 부족이면 `unavailable` 마킹 후 부분 튜닝).

## 1. 형식 검증

**무엇을 보는가**: 사용자가 붙여넣은 결과가 에이전트가 요청한 수집 SQL의 산출물 형식과 일치하는가.

| 점검 항목 | 기준 |
|-----------|------|
| 컬럼 시그니처 | 요청한 SQL의 SELECT 컬럼 목록과 응답 헤더가 동일한가 |
| 행 구분 | 결과가 텍스트/표 형식으로 식별 가능한가(들여쓰기·구분자 정합) |
| 인코딩 | 한글·특수문자가 깨지지 않았는가 |
| 잘림 | 끝 행이 잘리지 않았는가(`...`로 끝나면 잘림 의심) |

**실패 시 행동**: 어떤 SQL의 결과를 받기를 기대했는지 다시 안내하고, 동일 수집 SQL을 재제시한다. 잘림이 의심되면 `WHERE` 필터를 좁혀 분할 수집을 권고.

## 2. 완전성 검증

**무엇을 보는가**: 요청한 모든 테이블/인덱스/컬럼/파라미터에 대한 정보가 포함되었는가.

| 점검 항목 | 기준 |
|-----------|------|
| 테이블 통계 | `parsed_sql.tables`의 모든 테이블에 대해 `NUM_ROWS, BLOCKS, AVG_ROW_LEN, LAST_ANALYZED` 4개 컬럼 모두 존재 |
| 컬럼 통계 | WHERE/조인/정렬에 사용된 모든 컬럼에 대해 `NUM_DISTINCT, NUM_NULLS, DENSITY, HISTOGRAM` 4개 컬럼 모두 존재 |
| 인덱스 | 대상 테이블별 최소 1개 이상의 인덱스 행, 각 인덱스에 `INDEX_NAME, UNIQUENESS, COLUMN_NAME, COLUMN_POSITION` |
| 실행 계획 | `Plan hash value` 또는 `Id`/`Operation` 헤더가 식별되며, 최종 행이 `Rows`/`Bytes` 컬럼을 포함 |
| 바인드 | SQL이 바인드 변수를 사용하는데 사용자가 대표값을 제공하지 않았으면 미충족 |

**실패 시 행동**: 누락된 항목만 재요청. `[수신 완료]`에 받은 항목, `[아직 필요]`에 누락 항목, `[재요청 수집 SQL]`에 해당 항목 수집 SQL을 정확히 같은 형식으로 다시 제공한다.

## 3. 일관성 검증

**무엇을 보는가**: 서로 다른 정보 간의 충돌·괴리가 없는가. 임계값을 넘는 괴리는 통계 노후화나 응답 오류를 강하게 시사한다.

| 점검 항목 | 임계값 / 기준 | 의심 원인 |
|-----------|---------------|-----------|
| `USER_TABLES.NUM_ROWS` ↔ 실행 계획 `Rows` 추정치 | **10배 이상** 괴리 | 통계 노후화 또는 히스토그램 부재 |
| `E-Rows` ↔ `A-Rows` (실측 가용 시) | **10배 이상** 괴리 | 카디널리티 오추정. 통계 수집 또는 히스토그램 권고 |
| 인덱스 `NUM_ROWS` ↔ 테이블 `NUM_ROWS` | **20% 이상** 차이 | 인덱스 통계 노후화 또는 부분 인덱스 |
| `CLUSTERING_FACTOR` ↔ 테이블 `BLOCKS` / `NUM_ROWS` | CF가 NUM_ROWS에 가까우면 매우 낮은 클러스터링 | 인덱스 스캔 후 랜덤 I/O 과다 우려 (튜닝 가설 단서로 활용) |
| WHERE 컬럼이 NUMBER인데 바인드가 문자열 표기 | 타입 불일치 | 암묵적 형 변환으로 인덱스 미사용 가능성 |

**실패 시 행동**: 모순을 명시적으로 지적("ORDERS.NUM_ROWS=1억인데 실행 계획 Rows 추정치=2,000으로 약 50,000배 괴리")하고, 사용자에게 ① 통계 재수집 ② 정확한 결과 재제출 중 선택을 요청.

## 4. 유효성 검증

**무엇을 보는가**: 제공된 값 자체가 신뢰할 만한가.

| 점검 항목 | 기준 | 행동 |
|-----------|------|------|
| `LAST_ANALYZED` | 30일 초과 → 경고, 90일 초과 → 강한 경고 | `DBMS_STATS.GATHER_TABLE_STATS` 권고를 응답 상단에 노출 |
| `NUM_ROWS` 통계 NULL 또는 0인데 테이블이 비어있지 않을 가능성 | 통계 미수집 의심 | 통계 수집 후 재제출 권고 |
| 컬럼 통계 `NUM_DISTINCT` NULL 또는 1 | 히스토그램·통계 부재 | `FOR ALL INDEXED COLUMNS SIZE AUTO` 등으로 재수집 권고 |
| 실행 계획에 `dynamic statistics used` 언급 | 통계 부재로 동적 샘플링 사용 | 정적 통계 수집을 우선 권고 |
| `OPTIMIZER_FEATURES_ENABLE`이 DB 버전과 다름 | 비표준 환경 | 사용자 의도 확인 후 진행 |

**실패 시 행동**: 즉시 `INFO_REQUEST`로 돌아가지 않아도, 응답에 **경고를 누적 기록**하고 `TUNING`에서 가설 후보로 활용. 너무 심각한 경우(예: 통계 NULL)에만 재요청.

## 5. 재요청 응답 템플릿 (FR-4)

검증이 부족/이상으로 끝났을 때의 응답은 다음 3섹션을 **정확한 헤더 텍스트로** 사용한다(자동 회귀 테스트가 헤더 매칭으로 통과 여부를 측정).

```
[수신 완료]
- DB 버전: 19c
- 실행 계획: ORDERS에 FULL TABLE SCAN 확인
- 테이블 통계: ORDERS 1억 건, CUSTOMERS 500만 건
- 인덱스: ORDERS에 PK_ORDERS(ORDER_ID)만 존재

[아직 필요]
1. ORDERS.ORDER_DATE, ORDERS.STATUS의 컬럼 통계
   - 이유: 두 컬럼이 WHERE 조건이므로 선택도 판단에 필수.
2. 바인드 변수 :B1, :B2의 대표 값과 조건 카디널리티
   - 이유: 바인드 값에 따라 적합한 접근 경로가 달라짐.

[재요청 수집 SQL]
-- (1) 컬럼 통계
SELECT column_name, num_distinct, num_nulls, density, histogram
FROM   user_tab_col_statistics
WHERE  table_name = 'ORDERS'
  AND  column_name IN ('ORDER_DATE', 'STATUS');

-- (2) 카디널리티 측정
SELECT COUNT(*) FROM orders
WHERE order_date >= :B1 AND status = :B2;
```

규칙:
- `[수신 완료]`에는 받은 항목과 **핵심 수치**(행 수, 판단에 필요한 핵심 결과)를 1~2줄씩 인용.
- `[아직 필요]`는 항목당 ① 무엇이 ② 왜 필요한지 1문장.
- `[재요청 수집 SQL]`은 항상 한 줄 주석 + 세미콜론 종결.
- `iteration_count`는 사용자가 응답할 때마다 +1.

## 6. 권한 부족 처리

사용자가 "권한이 없어 제공할 수 없다"고 명시한 항목은:

1. `info_requirements` §4의 대체 경로(`USER_*`→`ALL_*`→`DBA_*`)를 한 번 더 안내.
2. 그래도 불가능하면 `collected_info.unavailable[]`에 추가.
3. 응답에 한계 고지 한 줄을 박는다. 예: `※ 컬럼 히스토그램 미확인으로 카디널리티 진단 정밀도가 낮음.`
4. 부분 튜닝으로 진행 가능한 시점에 `TUNING`으로 전이. 단 `output_format` 모듈의 `[튜닝 대안]`에 **추정 효과 폭이 넓다는 점**을 명기.

## 7. 금지 표현 재확인

검증 결과 메시지에서도 `role` 모듈의 금지 표현(경험상/일반적으로/보통은/아마도/대체로)을 사용하지 않는다. 모든 의심·경고는 **임계값과 근거 수치**로 표현한다.
